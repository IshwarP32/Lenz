What We're Building

Project Overview

Lenz combines the best of Goodwy Right Gallery (an open-source Android gallery) with a custom Google Drive sync engine inspired by FolderSync.

🖼️

Local Gallery

Browse, search and organize photos & videos stored on your Android device. Inherited from Right Gallery's polished media viewer.

☁️

Google Drive Tab

A dedicated Cloud tab to browse, preview and download photos directly from your Google Drive without leaving the app.

🔄

Sync Engine

FolderPair-based sync with one-way and two-way modes, delta sync (SHA-256 checksums), and scheduled background sync via WorkManager.

🔐

Privacy First

No trackers, no telemetry. OAuth 2.0 with minimal scopes. Your photos stay yours — sync only what you choose.

Phase 1 ~1 day

Environment Setup

Install Android Studio, SDK, JDK, Git, and configure your development environment for Android/Kotlin development.

💻 System Requirements

  • ✓ OS: Windows 10/11, macOS, or Linux
  • ✓ RAM: 16 GB recommended (8 GB minimum — will be slow)
  • ✓ Storage: 40 GB+ free SSD space
  • ✓ CPU: Multi-core processor with hardware virtualization enabled (BIOS/UEFI: Intel VT-x or AMD-V)

📥 Installation Steps

  • ✓
    Install JDK 17+ — Download from Adoptium (recommended) or Oracle. Android Studio bundles a JDK, but having a standalone one is useful for command-line Gradle.
  • ✓
    Install Android Studio — Download from developer.android.com/studio. During setup, ensure these components are selected:
    • Android SDK
    • Android SDK Platform-Tools
    • Android Virtual Device (Emulator)
  • ✓
    Install Git — Download from git-scm.com. Configure your identity:
Terminal
git config --global user.name "Your Name" git config --global user.email "your.email@example.com"

⚙️ SDK Configuration

  • ✓
    Open Android Studio → Settings → Languages & Frameworks → Android SDK
  • ✓
    Install the latest API level (currently API 35 — Android 15) plus API 34 (for broad compatibility)
  • ✓
    Under SDK Tools tab, install: Android SDK Build-Tools, Android Emulator, Android SDK Platform-Tools, Google Play services

📱 Set Up Test Device

  • ✓
    Emulator: In Android Studio → Device Manager → Create Virtual Device → choose Pixel 8 or Pixel 9 → select a system image → Finish
  • ✓
    Physical Device (recommended for gallery app):
    1. Go to phone Settings → About Phone → tap "Build Number" 7 times
    2. Go to Settings → Developer Options → enable "USB Debugging"
    3. Connect via USB, accept the RSA key prompt on the phone
💡
Tip: A physical device is strongly recommended for testing gallery apps — you need real photos, camera access, and accurate performance measurements that emulators can't fully replicate.

☁️ Google Cloud Project (Do This Now)

  • ✓
    Go to Google Cloud Console → Create a new project named "Lenz"
  • ✓
    Navigate to APIs & Services → Library → Search for and enable "Google Drive API"
  • ✓
    Go to APIs & Services → OAuth Consent Screen → Configure as "External" → Add app name, email, and branding
  • ✓
    Go to Credentials → Create two OAuth 2.0 Client IDs:
    1. Android type — enter your package name (com.lenz.app) and debug SHA-1 fingerprint
    2. Web application type — needed for token exchange
ℹ️
Get your SHA-1 fingerprint: Run this command in the terminal. The password is usually android.
Terminal (Windows)
# Windows — find your debug keystore SHA-1 keytool -list -v -keystore "%USERPROFILE%\.android\debug.keystore" -alias androiddebugkey -storepass android # macOS / Linux keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android

Phase 2 ~3-4 weeks

Learn Android Fundamentals

Build foundational Kotlin and Android skills through Google's official course and hands-on mini-projects before touching the gallery codebase.

📘 Week 1-2: Kotlin & Compose Basics

  • ✓
    Start the official course: Android Basics with Compose — This is free, comprehensive, and the gold standard for beginners in 2026.
  • ✓
    Kotlin core concepts to master: Variables, types, null safety (?, !!, ?.let{}), functions, lambdas, data classes, sealed classes, extension functions, collections (map, filter, forEach)
  • ✓
    Jetpack Compose basics: @Composable functions, state management (remember, mutableStateOf), layouts (Column, Row, Box, LazyColumn, LazyVerticalGrid), Material Design 3 components
⚠️
Do not skip this phase! Jumping directly into Right Gallery's codebase without understanding Kotlin, Compose, and the Activity lifecycle will result in weeks of frustration. This investment pays for itself many times over.

🔨 Week 2-3: Build Mini-Projects

Build these small apps to cement your understanding. Each one teaches concepts you'll need for Lenz.

  • ✓
    Project 1 — "Hello Gallery": Display a grid of placeholder images using LazyVerticalGrid. Learn Compose layout, state, and navigation.
    Concepts: Compose basics, grid layout, navigation
  • ✓
    Project 2 — "Photo Loader": Load actual device photos using MediaStore API and display them in a grid with Coil/Glide.
    Concepts: Android permissions, MediaStore, image loading libraries
  • ✓
    Project 3 — "Note Saver": A simple notes app with Room database. Add, edit, delete notes.
    Concepts: Room, ViewModel, MVVM pattern, Coroutines
  • ✓
    Project 4 — "API Explorer": Fetch data from a public REST API (e.g., Unsplash) and display it. Add pull-to-refresh.
    Concepts: Retrofit/Ktor, Coroutines, error handling, loading states

🧠 Week 3-4: Key Concepts Deep Dive

  • ✓ Activity Lifecycle: onCreate → onStart → onResume → onPause → onStop → onDestroy
  • ✓ ViewModel: Survive configuration changes, expose UI state via StateFlow
  • ✓ Kotlin Coroutines: launch, async, withContext(Dispatchers.IO), Flow
  • ✓ Dependency Injection with Hilt: @HiltAndroidApp, @AndroidEntryPoint, @Inject, @Module, @Provides
  • ✓ Permissions: Runtime permission requests, READ_MEDIA_IMAGES, READ_MEDIA_VIDEO (Android 13+)
  • ✓ Navigation: Jetpack Navigation, NavHost, passing arguments between screens
  • ✓ Scoped Storage (Android 11+): How MediaStore replaces direct file access

📝 Example: A Simple ViewModel

Kotlin
@HiltViewModel class GalleryViewModel @Inject constructor( private val mediaRepository: MediaRepository ) : ViewModel() { private val _photos = MutableStateFlow<List<Photo>>(emptyList()) val photos: StateFlow<List<Photo>> = _photos.asStateFlow() init { loadPhotos() } private fun loadPhotos() { viewModelScope.launch { mediaRepository.getLocalPhotos() .collect { photoList -> _photos.value = photoList } } } }

// Step 1: Sign in with Credential Manager val credentialManager = CredentialManager.create(context) val googleIdOption = GetGoogleIdOption.Builder() .setServerClientId("YOUR_WEB_CLIENT_ID") .setFilterByAuthorizedAccounts(false) .build() // Step 2: Request Drive authorization (separate step) val authRequest = AuthorizationRequest.Builder() .setRequestedScopes(listOf(Scope(DriveScopes.DRIVE_FILE))) .build() val authResult = Identity.getAuthorizationClient(context) .authorize(authRequest) .await()

  • ✓

  • ✓

// Initialize Google Drive service val credential = GoogleCredential().setAccessToken(accessToken) val driveService = Drive.Builder( GoogleNetHttpTransport.newTrustedTransport(), GsonFactory.getDefaultInstance(), credential ).setApplicationName("Lenz").build() // List image files from Drive suspend fun listPhotos(folderId: String?): List<DriveFile> = withContext(Dispatchers.IO) { val query = buildString { append("mimeType contains 'image/' and trashed = false") folderId?.let { append(" and '$it' in parents") } } driveService.files().list() .setQ(query) .setFields("files(id, name, mimeType, thumbnailLink, modifiedTime, size)") .setPageSize(100) .execute() .files.map { it.toDriveFile() } }

Phase 6 ~3-4 weeks

Sync Engine

The most complex phase — build a FolderPair-based sync engine with delta sync, conflict resolution, scheduled background execution via WorkManager, and progress UI.

🗄️ Step 1: Design the Data Model

  • ✓
    Create Room entities for sync state management
Kotlin — Room Entities
@Entity(tableName = "folder_pairs") data class FolderPair( @PrimaryKey(autoGenerate = true) val id: Long = 0, val localPath: String, // e.g., "/storage/emulated/0/DCIM/Camera" val remoteFolderId: String, // Google Drive folder ID val remoteFolderName: String, // Human-readable name val syncDirection: SyncDirection, // UPLOAD, DOWNLOAD, TWO_WAY val conflictPolicy: ConflictPolicy, val isEnabled: Boolean = true, val scheduleMinutes: Int = 60, // Sync interval val lastSyncTime: Long? = null, val lastSyncStatus: SyncStatus = SyncStatus.NEVER_SYNCED ) enum class SyncDirection { UPLOAD, DOWNLOAD, TWO_WAY } enum class ConflictPolicy { NEWEST_WINS, LOCAL_WINS, REMOTE_WINS, SKIP } enum class SyncStatus { NEVER_SYNCED, SUCCESS, FAILED, IN_PROGRESS } @Entity(tableName = "sync_records") data class SyncRecord( @PrimaryKey(autoGenerate = true) val id: Long = 0, val folderPairId: Long, val fileName: String, val localChecksum: String?, // SHA-256 val remoteChecksum: String?, // SHA-256 from Drive val localModified: Long?, val remoteModified: Long?, val lastSyncedAt: Long )

🔄 Step 2: Implement Sync Logic

The sync algorithm follows a three-phase approach inspired by FolderSync:

  • ✓
    Phase A — Inventory: List all files in local folder and remote folder. Compute checksums for local files, retrieve checksums from Drive metadata.
  • ✓
    Phase B — Diff: Compare against the last-synced state (from SyncRecord). Categorize each file as: NEW_LOCAL, NEW_REMOTE, MODIFIED_LOCAL, MODIFIED_REMOTE, MODIFIED_BOTH (conflict), DELETED_LOCAL, DELETED_REMOTE, UNCHANGED.
  • ✓
    Phase C — Execute: For each diff result, perform the appropriate action (upload, download, delete, or resolve conflict) based on the sync direction and conflict policy.
ℹ️
Delta Sync: Never re-upload/download unchanged files. Compare SHA-256 checksums + last-modified timestamps. Google Drive provides md5Checksum and sha256Checksum in file metadata — use these to avoid re-downloading files for comparison.

⏰ Step 3: WorkManager Integration

  • ✓
    Create SyncWorker extending CoroutineWorker
  • ✓
    Use enqueueUniquePeriodicWork with ExistingPeriodicWorkPolicy.KEEP
  • ✓
    Set constraints: NetworkType.CONNECTED (or .UNMETERED for large syncs), setRequiresBatteryNotLow(true)
  • ✓
    Return Result.retry() for transient errors (network timeout), Result.failure() for permanent errors (auth revoked)
  • ✓
    For syncs exceeding 10 minutes, call setForeground() and show a progress notification
Kotlin — SyncWorker
@HiltWorker class SyncWorker @AssistedInject constructor( @Assisted context: Context, @Assisted params: WorkerParameters, private val syncManager: SyncManager ) : CoroutineWorker(context, params) { override suspend fun doWork(): Result { val pairId = inputData.getLong("PAIR_ID", -1) if (pairId == -1L) return Result.failure() return try { // Show notification for long-running sync setForeground(createForegroundInfo()) syncManager.syncFolderPair(pairId) Result.success() } catch (e: IOException) { Result.retry() // Transient error } catch (e: AuthException) { Result.failure() // Permanent error } } } // Schedule periodic sync for a folder pair fun scheduleSyncForPair(pair: FolderPair) { val request = PeriodicWorkRequestBuilder<SyncWorker>( pair.scheduleMinutes.toLong(), TimeUnit.MINUTES ).setConstraints( Constraints.Builder() .setRequiredNetworkType(NetworkType.CONNECTED) .setRequiresBatteryNotLow(true) .build() ).setInputData( workDataOf("PAIR_ID" to pair.id) ).build() WorkManager.getInstance(context) .enqueueUniquePeriodicWork( "sync_pair_${pair.id}", ExistingPeriodicWorkPolicy.KEEP, request ) }

🎨 Step 4: Sync Settings UI

  • ✓ FolderPair List Screen: Show all configured folder pairs with their status (synced, syncing, error)
  • ✓ Add/Edit FolderPair Screen: Local folder picker + Drive folder picker + sync direction + conflict policy + schedule interval
  • ✓ Sync Progress: Show a progress indicator with file count (e.g., "Uploading 23/150 files...")
  • ✓ Sync History: Log of past syncs with timestamps, file counts, and any errors
  • ✓ Manual Sync Button: Allow users to trigger an immediate sync for any folder pair

🐛 Step 5: Handle Edge Cases

  • ✓ Network disconnection mid-sync → save progress, resume on reconnect
  • ✓ OAuth token expiration → refresh token before sync starts
  • ✓ Google Drive API quota exceeded → exponential backoff + retry
  • ✓ Large files (videos) → chunked upload/download with progress tracking
  • ✓ File renamed on one side → detect via file ID (Drive) or checksum match
  • ✓ Concurrent modifications (two-way conflict) → apply user's chosen conflict policy
  • ✓ Low storage on device → warn user before downloading, skip if insufficient

Phase 7 ~2-3 weeks

Polish & Release

Comprehensive testing, performance optimization, accessibility audit, and preparing for distribution (Play Store or F-Droid).

🧪 Testing

  • ✓ Unit tests: SyncManager diff logic, conflict resolver, checksum comparison, DriveRepository parsing
  • ✓ Integration tests: Room database operations, WorkManager scheduling
  • ✓ UI tests: Compose testing for navigation, states, and user flows
  • ✓ Manual testing: Test on multiple devices, API levels, and network conditions
  • ✓ Edge case testing: Airplane mode, low battery, large libraries (10,000+ photos), slow connections

⚡ Performance Optimization

  • ✓ Profile with Android Studio Profiler (CPU, Memory, Network)
  • ✓ Optimize image loading — proper caching, downsampling for thumbnails
  • ✓ Minimize API calls — batch Drive requests, cache metadata locally
  • ✓ Reduce battery drain — proper WorkManager constraints, avoid wake locks
  • ✓ Test cold start time — target under 2 seconds

♿ Accessibility

  • ✓ Content descriptions for all images and icons
  • ✓ Sufficient color contrast ratios (WCAG AA)
  • ✓ TalkBack navigation testing
  • ✓ Touch target sizes ≥ 48dp

🚀 Release Preparation

  • ✓ Generate release signing keystore (keep it safe — you can never change it!)
  • ✓ Configure ProGuard/R8 for code shrinking and obfuscation
  • ✓ Create Play Store listing: screenshots, description, privacy policy
  • ✓ OR prepare F-Droid metadata for open-source distribution
  • ✓ Submit for Google OAuth verification (required for Drive API in production)
  • ✓ Build signed APK/AAB and test on a clean device
⚠️
OAuth Verification: For Google Drive API access to work for external users, your app must go through Google's OAuth verification process. This can take 2-6 weeks and requires a privacy policy, homepage, and demo video. Start this process early!
